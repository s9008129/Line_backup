# LINE 相簿導覽失誤：根因分析草稿

本文件是 Planner 的研究結果，基準為 `66ebd9d50378d3b1d533c83eaf48eaca9a72ef43`。未執行修復、GUI 重現、模型對照或產品驗收。

## 結論

Skill 沒有要求按 Escape。當次 Agent 已讀取 Skill，仍在沒有當前畫面作用依據的情況下，把「返回列表」自行實現為 Escape。可見原因是錯誤的動作選擇；規格層的根因是「必須回到列表」與「如何判斷返回操作有據」之間有空白，且沒有處理交接入口為單本相簿頁的分支。

這不是使用不存在的工具：當次 CUA 明確有 `App.pressKey(key)`。問題是把 API 能派送某個鍵，當成該鍵在目前焦點中具有正確 LINE 導覽效果。正確工具仍能執行錯誤動作。

Agent 本來就應遵守 Skill 的可靠目標要求；文件缺口不免除這次執行錯誤。修正的目的是降低下一個執行者自行補出錯誤步驟的機會。

## 事件證據與限制

來源為本次對話可見的工具呼叫、回覆、截圖及使用者回報。下列是脫敏整理，不冒充平台完整 trace。原始截圖尚未另存成本任務的像素檔；本次不為了取得截圖重新操作 LINE。

| 1 | Owner 要求使用本專案 Skill 測試下載，指定預設資料夾並交出前景 | 使用者授權 |
| 2 | Agent 讀了 Skill、inventory、verified-experience、visual-grounding，並取得 CUA 說明 | 工具軌跡；不能說 Skill 完全沒載入 |
| 3 | 初始 AX 為空標題標準視窗，僅關閉、縮小與選單；截圖有單一本標題、20 張及照片網格，未見明確返回控制項 | 工具回覆與畫面 OBSERVED；未證明與舊列表的身分關聯 |
| 4 | Agent 呼叫下列程式，意圖是「返回相簿列表」 | 實際工具呼叫 |
| 5 | 後續 AX 的視窗標題為 LINE，截圖為聊天主畫面 | 工具回覆與畫面 OBSERVED |
| 6 | Owner 回報相簿視窗被關；Agent 承認自行假設 Escape 為返回 | 人工回報 OBSERVED、Agent 事後說明 |

```javascript
await lineApp.pressKey("Escape");
await lineApp.getAXStateAndScreenshot();
```

這條軌跡支持「原相簿視窗消失、聊天主畫面出現」，加上 Owner 觀察，支持這次 Escape 關閉了獨立相簿視窗。它不支持「退出 LINE」、「刪除相簿」或「照片遺失」。也不能推廣成所有 LINE 視窗按 Escape 都會關閉。

先前說明有一點需更正：當次確實做了操作後觀察，並非漏掉 `getAXStateAndScreenshot()`。失誤發生在操作前，不能只靠再要求「操作後觀察」修復。

## 從任務到工具的必要推理邊界

一個輸入能安全成立，需要依序確認：

1. **目標與授權**：Owner 要備份的是哪個交接對象，允許哪些副作用。
2. **目前狀態**：看到相簿列表、單本照片頁、選單、chooser、下載中，還是聊天／不明頁。
3. **動作作用的依據**：當前控制項或已驗證且匹配狀態的快捷鍵，確實支持預期轉換。
4. **派送能力**：CUA 有對應 API，目標／焦點與座標可可靠對應。
5. **結果核對**：動作後仍屬原任務脈絡，而且出現預期頁面；不符就停下查證。

當次第 1 項有明確使用者授權，第 4 項也有合法 API；第 2 項只知道是單本照片頁，第 3 項沒有證據。Agent 卻跨過第 3 項，以一般快捷鍵慣例完成派送。第 5 項有執行，但只能事後發現狀態已改變。

「每次輸入後觀察」是偵測，不等於事前防止錯誤；「正常可逆導覽不逐點請示」是授權效率原則，不是判定某個未知動作可逆的證據。

Skill 其實已有相關要求：`SKILL.md:20` 的「工具能可靠操作哪個目標」、`:39` 的當次列表與禁止自動改配，及 `verified-experience.md:45` 的身分不明停止，都應抑制這次猜測。因此不能將根因簡化為「沒寫禁止 Escape，所以 Agent 可以按」。

反過來，Skill 也不是只能呼叫逐字列出的所有鍵與 API；若這樣解讀，就會讓正常、已可靠定位的導覽也停住。要補的是選擇動作的判準，而非無限列舉按鍵黑名單。

## 簿記工具與 GUI 的界線

`daily.py:1–5` 明定不找、不點 GUI。`bound()` 在 `:391–408` 只核對本地 session 與證據引用；它不觀察 LINE，也無法攔截原生 CUA 的 `pressKey()`。`summary()` 在 `:1918–1924` 明列 `sensor_verified=false`、`real_line_e2e=NOT_TESTED`、簿記判定範圍。

可見軌跡尚無本次 fresh bind／scan／intent，表示尚未形成新簿記進度。這不表示 Owner 沒有交接或沒有 GUI 授權。intent 是 Save All 前的持久保留，不是所有唯讀觀察與一般導覽的通行證。本次尚無 Save All，不能用「少了 intent」解釋 Escape。

把更多 JSON 欄位塞進 daily 不會自動約束直接 CUA 輸入。若要對所有模型強制阻擋某類鍵，必須由真正的輸入控制層限制能力；那會改變本專案架構與能力邊界，不能偽裝成這次最小 Skill 修補。

## 不足以成立的其他解釋

- **Skill 沒載入**：可見讀檔軌跡反證這個簡單解釋；「載入」也不等於「每項規則正確落實」。
- **文件太長或記憶輸出太多**：本次 memory 曾輸出大量資料，但沒有控制實驗證明這導致 Escape；可列為後續可測假說，不列主因。
- **官方工具指示按 Escape**：CUA 說明只有 `pressKey` 能力，沒有把 Escape 定義為 LINE 返回鍵。
- **只有加入禁止 Escape 就夠**：仍留下 Command-W、關閉按鈕或不明 Return 等同類猜測。
- **全面禁止鍵盤即可**：會破壞既有 chooser 的前往資料夾及已核對 Return 流程。
- **全停住最安全，所以一律請 Owner 點**：會違背自主盤點與正常可逆導覽的產品目標。

## 修正方向

建立最小入口分支與可觀察的動作條件；明列本次反例，但不把單一鍵當全部根因。保留有據動作的自主進展，用正向與反向案例共同驗證。具體切片、寫入範圍、檢查責任與停止條件見 [plan.md](plan.md)。
