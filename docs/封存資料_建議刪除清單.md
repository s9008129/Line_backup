## A：可考慮刪除一份已核對副本

63 項含 18 個 Swift 建置／module cache 目錄、7 個 Python `__pycache__`、11 個 `.DS_Store` 及 27 篇舊 Markdown。歷史 task 的部分程式或 manifest 引用建置產物；若刪除 removed-from-active 副本，從保留的 worktree 快照仍可恢復它們。這不表示舊活躍路徑仍存在或歷史任務可原地重播。

## B：若連快取的兩份都刪除，可重建但失去精確歷史重現

僅適用 CSV 第 01–25 項（18 個 Swift build/cache 目錄與 7 個 Python bytecode cache），不包括 27 篇文件或 `.DS_Store`。若之後連 `removed-from-active/` 與 `worktree/` 兩份 cache 都刪除，現有來源可重新建置或產生 bytecode；對目前產品功能不受影響的工程信心約 95%（工程判斷，非統計保證）。重新建置不保證產生相同二進位，也會失去歷史 task 的精確 binary 重播能力；部分 task 原地重播需要由程式碼重新建置快取。這類刪除須先由 Owner 決定，並在產品測試完成後再評估。

`rev28/.build`、正式 `runtime/bin`（包含 image decoder）、grant、ledger、state、照片、原始 screenshots/evidence 均不在 CSV，任何後續清理都不得把它們納入此類。

27 篇舊 Markdown 雖沒有活躍程式／測試的檔名引用，仍是規劃與交接歷史。可依 A 僅考慮移除 removed-from-active 副本，但至少保留 worktree 中的一份。照片、原始 evidence/screenshots、state、grant、ledger、未追蹤原創資料及 `all-refs.bundle` 不屬於本次 63 項 allowlist，不能據此清單整體刪除；每類都至少保留一份，另依其既有保護規則處理。

## 永久刪除前的重驗條件

1. Owner 先選定 A 或 B 的精確項目。不能用「清除所有快取」等寬泛條件替代逐項清單。
2. 刪除前，逐項重新核對待刪副本與 `pre-move-manifest.json`、仍保留的 worktree 副本：每個節點的相對路徑、SHA-256、大小、型別及 symlink target 都必須吻合。A 預期 63 項／53,983 節點；B 僅限 CSV 第 01–25 項。
3. 確認 worktree 快照及 1,275 項 preservation baseline 仍完整、沒有執行中程序持有目標，並確認 protected runtime/bin 與 `rev28/.build` 仍在原位。
4. 任一檔案缺失、雜湊／大小／型別／target 不符、scope 多出項目或程序占用時，停止刪除並保留現況，交 Owner 裁決。

**空間回收限制：**本次約 3.41 GiB 是一般檔案的邏輯位元組總量。封存使用 APFS clone 時，刪除 clone 副本不保證能回收同等的實體磁碟空間。
