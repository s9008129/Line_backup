## 4. 為什麼 key 會不同

### 4.1 程式契約

`src/line_backup_batch/notes.py:208` 的 `post_key()` 先驗證 `list_key` 與完整 POST identity，再呼叫 `_identity_key()`；`src/line_backup_batch/notes.py:160` 的 `_identity_key()` 對 canonical JSON payload 做 digest。這是既有的身分計算契約，不是本次新增的行為。

因此：

1. identity 的任一欄位不同，`post_key` 就會不同。
2. `text_anchor` 變短會改變 key；`visual_key` 變短也會改變 key。
3. page 10 的輸入 identity 與 result identity 一致，所以 result 的 key 可由輸入 identity 解釋。
4. statement／ledger 寫的是另一個歷史 identity 的 key，兩者不能互相認領。

### 4.2 不是已證實的 CLI hash 錯誤

本報告沒有把「key 不同」直接歸因於 CLI bug。現有證據反而顯示：

- `page-10-posts.json` 的 identity hash 是 `78990e…22f9`。
- `page-10-result.json` 的 identity hash 也是 `78990e…22f9`。
- 歷史 event 53 的 identity hash 是 `4d07d8…3ca38`。
- 三者是不同輸入內容，不是同一個 identity 被算出兩個結果。

因此，這是**輸入 identity 不一致**，不是已證實的 hash 實作錯誤。真正造成輸入 identity 被縮短的原因仍是 `UNKNOWN`。

## 5. 觸發停止的規則

停止規則位於 `.agents/skills/line-notes-agent-cua/references/evidence-template.md:2408`。原文的關鍵句是：

> `page` 成功後，才把回傳的實際 key 與事件讀回補到同一份紀錄；讀回若與提交成員或來源對應有差異，立即停止後續 page、`finish`、新 intent 與下載，且不得以 `evidence-correct` 改寫 page 成員。

套用到本輪：

- `source_to_rows`：statement／ledger 說 `source_order=14` 對應歷史 key `7b21…576b`。
- `rows_to_source`：page 10 回傳的 `source_order=14` 對應新 key `7a51…dfd6`。
- 兩者無法同時成立；summary 也確實出現兩個 `source_order=14`。
- 因此 page gate 失敗，Agent 必須停止後續 page、finish、新 intent 與下載。
- 不能用 `evidence-correct` 把 page 成員改成歷史 key；也不能用新 scan 掩蓋本輪錯誤。

這條規則不是 CLI 的 exit code 4／70 業務拒絕，也不是 LINE 的下載錯誤；它是 Agent 在 page 提交與讀回之間的人工對帳 gate。
