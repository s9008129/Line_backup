- `references/gui-inventory.md:7-10`：入口須以當次 AX／截圖／可見畫面核對；疑似聊天、相簿或出處不明頁面時停止新派送並先唯讀釐清。

- `references/gui-inventory.md:172`：`ENTRY_LOST` 與 `INPUT_UNAVAILABLE` 可同時成立，必須分開記錄。
- `references/gui-inventory.md:174-181`：有界恢復階梯；無新證據不重試，無法安全取得同一前景時進 `HANDOFF_REQUIRED`。

- `ENTRY_LOST` 已由當次截圖與聊天標題正面支持，不是 `RETURN_NOT_OBSERVED`。
- 初次 bind 確實看到列表，因此不能說「整場任務從未看到記事本」。
- 現有證據不能證明是 media 2 recovery、下載、LINE UI 或 CUA 造成；根因 `UNKNOWN`。
- 不可把 `foreground=VALID` 解讀成入口仍可用：前景有效只代表 app／window 綁定仍有效，不代表指定列表仍在前景或入口控制仍可達。

#### 影響

在此之後，新 scan、媒體細盤、下載或 reveal 都不能以同一入口安全繼續；依規則停止依賴該前提的派送，但可保留既有完成與其他唯讀證據。

## 8. 已排除的假異常

以下項目容易被誤報，應明確排除：

1. **media 2 不是 UNKNOWN v5**：舊 attempt 的 outcome 是 `STOPPED`，新 attempt 有 `recovery_of`，是精確 recovery；沒有 v5 isolation 事件。
2. **最新 `status_counts` 不是全 0**：`COMPLETED=2`；但這只代表 current scan scope 的 2 個媒體，不代表全列表。
3. **`current_incomplete=0` 不代表全列表完成**：16 篇仍是 `DETAIL_PENDING`，`all_known_media_complete=false`。
4. **舊 `summary-after-bind` 的 unresolved STOPPED 不是現行未解 blocker**：它是 sequence 34 的舊投影；media 2 recovery 與 completion 在它之後。
5. **`noWindowsAvailable` 未證明是 LINE bug**：底層原因 `UNKNOWN`；不可把錯誤字串直接寫成產品缺陷。
6. **初次 bind 確實有記事本列表**：不能寫成整場任務從未看到列表。
7. **聊天頁標題是 `LIST_REDACTED (11)`**：不可省略 `(11)` 或誤認成另一個列表。

11. **不可清理舊 staging、重下 media 2、改寫 completion 或建立新 scan 解鎖入口**：這些都會越過目前的安全邊界。
12. **`.local/.../download-check...stdout.json` 是 completion event wrapper，不是獨立 verifier JSON**：只可引用其中 nested verification 與 completion 投影。

1. macOS CUA 在 `ENTRY_LOST`、AX 不暴露控制、pointer 回 `-10005 noWindowsAvailable` 三者同時出現時，是否存在安全、可重現的 window handle reacquire 路徑？若有，正確 API 形狀與必備證據是什麼？
