## Decision basis

The current task is BLOCKED, the issue is WAIT_HUMAN, c6 consumed its only continuation, zero retries remain, and G0–G3 are respectively BLOCKED / NOT_RUN / NOT_RUN / NOT_RUN. These are accepted handoff facts; this review did not re-open the 28-gate inventory or attempt history. The original 28 required gates remain intact.

Route A is closed by two source branches. `resume` only calls `inspect` and renders state (`cli.py:305–323`). `reconcile` first rejects any pending issue with `ControllerError("unresolved/exhausted issue requires human resolution; routing cannot reset its ledger")` (`controller.py:1878–1879`). If that guard were absent, c6's `BLOCKED` candidate still fails the source's accepted-run requirement for REPLAN (`controller.py:1880–1892`). Replaying a previously consumed decision cannot restore a historical route after state changes (`controller.py:2102–2106`).

Route B is closed by the issue ledger. A lineage link adds the task and records `ISSUE_LINKED`, leaving the existing issue state and count intact (`escalation.py:169–181`). `authorize` accepts only an unused `ANALYSIS_RETURNED` continuation and raises `EscalationError("no unused bounded continuation")` when the current `WAIT_HUMAN` state or nonzero continuation count is substituted (`287–318`). `guard_task` permits allocation only for `CONTINUATION_AUTHORIZED`, then records it as consumed (`320–358`). Current task state has no eligible `next_stage`; a new issue root would create a separate budget rather than restore the original one.

The direct recovery-command dependency does not change that result. `recover-inspect` is read-only and reports prior review/continuation counts as `UNKNOWN`. `recover-prepare` requires a human decision for `FRESH_PLAN`, then creates `TASK-RECOVERY-*` with stage PLAN, no contract, an empty `required_gates` array, and inherited counts `UNKNOWN` (`migration.py:65–125`). This is not a same-task continuation and cannot preserve the original 28 gate definitions and known consumed issue budget. `migrate --mode fork` requires recorded authority and a new destination; it preserves copied history without recertifying it, but does not resolve/admit the original IssueLedger (`42–62`). These commands were read only and not executed.

For an authorized issue continuation, result admission first validates role-owned required gates (`controller.py:1595–1601`), then defines success as completed runtime plus candidate `PASS` (`1613–1614`) and passes that same outcome to `finish_task_run` (`1631–1638`). The issue ledger requires the exact bounded success criterion with nonempty verified files; a proven `TARGETED_DIAGNOSTIC` still becomes `DIAGNOSTIC_COMPLETE_WAIT_HUMAN` (`escalation.py:369–387`). A remaining pending issue keeps the task BLOCKED (`controller.py:1639–1642`). Only a passed IMPLEMENT stage advances to implementation complete; CRITICAL work routes to independent Acceptance (`controller.py:2291–2300`). The source behavior therefore does not support treating a local diagnostic as a completed full IMPLEMENT result. This is a control-flow observation; it does not establish why the original workflow reached the current deadlock.

## Bounded governance specification

This is a decision specification, not an instruction to implement or execute a recovery. The governance owner must choose whether to keep STOP or separately authorize a finite design proposal within these boundaries:

1. **Exact deadlock:** The original continuation is consumed, but its final issue state is `WAIT_HUMAN`. `finish_task_run` processes only `CONTINUATION_CONSUMED`; the ledger authorization path requires `ANALYSIS_RETURNED` and `continuations == 0`; `reconcile` refuses any unresolved issue; task state has no eligible stage. Therefore neither same-issue authorization nor allocation is reachable through the reviewed entrances.
2. **Safety stop and workflow tension (inference):** The source enforces a safety stop around unresolved/exhausted issues. Its stage-wide `passed` value couples issue completion to a completed runtime, candidate `PASS`, and the current IMPLEMENT role-owned gates. This may conflict with an intended partial-repair workflow that wants to retain verified local progress without declaring full IMPLEMENT complete. That tension is an inference from control flow; the source review does not establish design intent, and retained evidence has not been shown here to prove c6's local success criterion.
3. **Existing procedure and immutable release:** No inspected existing entry performs a same-task, same-issue, non-reset transition while retaining all gate metadata. `recover-prepare` requires a human decision but creates a new fresh-PLAN task with no gates and unknown inherited counts; `migrate --mode fork` copies history without admitting the original issue. Those procedures do not solve this constraint. The immutable v4.8.0 bytes may remain archived unchanged, but that alone does not make the blocked task admissible.
4. **Smallest potential boundary:** If governance does not keep STOP, separately approve designing an issue-scope, evidence-qualified resolution followed by controlled reactivation of the original task. Do not reset/reopen the issue as a new root, create a new task, repeat the continuation, alter the plan/gates, or broadly redesign unrelated Controller behavior. Any release-binding or compatibility change requires its own explicit approval and independent review.
5. **History and idempotency invariants:** Bind any future decision to the original task, issue, c6 run, selected source/contract identity, bounded success criterion, and current terminal state. Preserve all original receipts and events; keep continuation count `1` and retries `0`; append an attributable, prospective, idempotent decision/event. 6. **No promotion of partial evidence:** Issue-local evidence may resolve only the bounded issue condition; it must not set `IMPLEMENTATION_STATUS=COMPLETE`, mark unearned gates PASS, or impersonate full task acceptance. Full IMPLEMENT admission must still satisfy all original required stage gates, and independent Acceptance remains required.
7. **Gate and scope invariants:** Preserve all 28 required gates byte-for-byte in their existing task contract and metadata, with their existing owner, phase, requiredness, evidence role, closure rule, and criticality. No waiver, scope expansion, altered owner, or gate removal is part of this proposal.

If the original bounded criterion cannot be independently verified from genuine retained evidence, keep STOP. Even if a governance transition is later approved, runtime binding and separate live LINE authorization remain required before any real G1–G3 action.
