## 給下一輪高階 Replanner 的指示

你是本專案下一輪的 Replanner。請在使用者提供本次 Implementer 完整結果後，先讀本報告、該輪 `E2E測試報告.md`、progress、implementation result、凍結 Plan／Handoff／機器契約，以及它們引用的原始收據、程式、截圖與狀態證據。以較新的實測修正本報告的暫態判斷，保留歷史失敗與仍然未知的事項。

新版 replan 必須把「最小真實連接，而且確實可用」放在首個產品里程碑：由真實 LINE 擷取取得原始資料，留存並讀回，再由正式辨識與原生旁證產生可供現有流程使用的 observation；不能把預填答案的測試替身當作實機連接。接著依必要安全條件完成第一本真實備份、回到列表並實際 bounded scroll、第二本不同相簿備份及檔案／狀態驗收。若須分輪，明列本輪要證明的真實能力與下一輪依賴；部分成功不得關閉完整目標。

每一步都要回答一個具體問題，明列可執行入口、實際資料來源、允許變更路徑、成功證據、停止條件、同一 root issue 的剩餘嘗試額度及下一步。先安排小而直接的實測來找出缺口，再補必要程式與針對性迴歸，不以大量離線 PASS 或文件交付替代實機證據。遵循 AGENTS.md 的「規劃 → implement → E2E 測試 → 原始證據回報 → replan」循環；不降低資料保全、身份、前景交接、下載至多一次或既有必要驗收條件。

本報告是檢討與下輪規劃輸入，不是新凍結計畫，也不授權當前 Implementer 擴大範圍。使用者已指定本對話主代理接任 Replanner；應先完成本報告，等 Implementer 結果到齊，再提出新版 replan。

## 1. 結論：真正讓我們反覆停在實機門外的原因

**主要根因是：規劃與驗證沒有足夠早地跑通一條最小、真實、可留證的產品連接，卻先完成許多分散元件及離線驗證。** 因而「能檢查一份已填好的辨識答案」與「能從真實 LINE 畫面產生那份答案」之間的缺口，到較晚階段才被發現。這是由歷次報告、真實 capture 研究及測試內容支持的因果判斷，不是對個別人或模型能力的猜測。[E02–E09]

**接續的直接阻塞，是驗證工具本身沒有先證明可正確執行與產生證據。** runner 的目錄推算錯誤導致錯誤 cwd 與範圍外收據；基線工具沒有完整處理特殊檔案與掃描失敗；本次 recovery 又出現「盤點時自己的輸出還在改變」的一致性失敗。結果，原本用來支持產品測試的工具，反而成為下一輪需要修復的對象。[E10–E14、E20–E22]

**放大因素是：每次工具事故都把進度帶入保全、報告與重新交接，但沒有強制把下一輪拉回一個可由真實測試回答的產品問題。** 文件與安全停機有必要；缺少的，是持續追蹤「這一輪究竟新增了哪個真實 LINE 能力」。使用者要求的迭代循環本身很清楚，執行順序與驗收粒度需要改進。[E01–E04、E16]

因此，責任同時涉及 Planner 的可行性假設與工作排序、Implementer 的具體程式／工具品質，以及跨輪整合與證據解讀。不能只歸因於 FIFO、使用者未交還前景、Harness 壞掉或「implementer 沒做事」。各責任的證據與界線見第 5 節。

## 3. 從第一性原理看：我們究竟必須證明什麼

完整自動備份必須逐項成立：

1. **看對：**程式從當下 LINE 畫面可靠確認群組、相簿日期與張數，以及同一 session／PID／window／layout 的連續性。
2. **做對：**用新鮮且有證據支持的目標，在 duplicate、目的地、owner、持久 intent、選單與至多一次派送條件成立後，發出 LINE 原生下載動作。
3. **收對：**實際收到完整檔案、驗證內容、提交並讀回狀態，正確釋放 owner。
4. **接著做：**回列表、實際有界滾動並確認新內容與 overlap，再對不同的 eligible 相簿重跑完整流程。

若第一條實際資料鏈不存在，後面的 transaction 再完整，也沒有可靠的真實輸入。若只有正確畫面而未下載、驗檔、提交狀態，也還沒有完成備份。[E01、E02]

最小真實連接應先建立以下可檢查鏈：

```text
真實 LINE 畫面與 AX
  → 原始 bytes 留存、hash 與 readback
  → 正式 analyzer + 必要原生窗口／幾何／frame support
  → 同一影格綁定的有效 observation
  → 現有 validator／catalog 流程實際接受並列出候選與 eligibility 理由
```

這條鏈的第一輪可以唯讀，不必為了測試 capture 就派送 Save All。它必須使用正式資料來源與實際接線；手動輸入日期／張數、stub analyzer、偽造 native support、截圖記憶體觀察，均不能替代完整證據。

測試應分清四層，並讓後續計畫依實測向前推進：

| 層級 | 可以回答的問題 | 仍不能證明 |
|---|---|---|
| 離線單元／契約測試 | 給定輸入時是否正確接受、拒絕、綁定與處理錯誤 | 真實畫面是否能產生正確輸入 |
| 真實唯讀連接 | 現場資料是否完整抵達正式辨識與下游，且有留存證據 | GUI 派送及下載是否成功 |
| 真實單本交易 | 身份、動作、下載、內容驗收與 state readback 是否完成 | 下一本與批次是否可靠 |
| 真實連續流程 | return／實際 scroll／新卡片 grounding／第二本交易是否成立 | 未測其他群組、版面或例外情境的普遍可靠性 |

「最小」應縮小一次要解的未知與實作面積；下載身份、資料安全與證據門檻仍須完整保留。

## 5. 根因、責任與應有改進

### R1：最小真實資料鏈證明得太晚——主要系統性根因

**事實：**live-grounding-03 Plan §9 已寫「先驗證真正 runtime process bridge、raw screenshot bytes、持續 kernel、同一 frame/action 綁定」。因此，不能說 Planner 完全沒寫前置條件。但大量實作與完整離線 suites 之後，仍停在未完成的真實 retained capture／analyzer／native 配對。[E03、E04、E08]

**因果推論：**前置條件停留在條文與假設，沒有足夠早成為帶有實際證據的第一個產品里程碑。下游元件的可用性，以注入正確分析結果的測試推進；真實 producer 的接線、型別、幾何與 phase 相容性，延後到整合時才一起暴露。

**Planner 責任：**完整列出 producer → retain → analyzer → native support → validator 的依賴；指定誰提供每一欄實測資料；先設計最短真實入口與可驗收輸出，而不是只描述理想資料格式。

**Implementer 責任：**將實際來源接到正式呼叫路徑，及早指出「只有注入接口、沒有 production 來源」；不能把 fixture 正例的成功解讀為真機能力。

**下輪方向：**先用新鮮真實 LINE 資料跑通唯讀鏈，產生 retained artifacts 與下游可用 observation；第一個斷點即是下一個待修問題。完整目標仍保留兩本交易與 scroll，不能在只有 capture 成功時結案。

### R2：測試證明「能拒絕錯誤／能驗證答案」，沒有充分證明「合法真實路徑能成功」

**事實：**分類測試正例的 surface 是 `ALBUM_DETAIL` 且沒有卡片。`live_classifier.mjs` 的 ALBUMS boundary 檢查使用已排序的 keys，卻和未排序字串比較：

```javascript
Object.keys(proof).sort().join(',') ===
  'version,frame_id,session_id,source,indicator_index,minimum,maximum,value'
```

實際排序應為 `frame_id,indicator_index,maximum,minimum,session_id,source,value,version`。兩者必然不同，使合法列表 proof 也無法通過該分支；detail fixture 不會走到這裡。[E05、E06、E08]

真實 CUA 回傳的 Buffer 同時呈現 `ArrayBuffer.isView=true`、`instanceof Uint8Array=false`。同 realm 的假資料不能揭露這個錯誤。後來已有 adapter 修正，最新離線 31 tests 也包括相關回歸；仍不證明完整 live chain 成功。[E08、E10、E19、E23]

**責任：**Planner 的驗收須涵蓋實際需要成功的 surfaces 與 phase；Implementer 須設計合法 ALBUMS／card 正例、真實來源樣本與 production 接線測試。只加更多拒絕案例，無法證明備份可用。

**下輪方向：**取下一輪留存的真實圖像與 AX 作可重播回歸，再做 fresh live acceptance；兩者分列。補充 schema 順序、cross-realm／subarray、`intersectionPx` 傳遞、chooser 各 phase 合法欄位等直接相關測試。不要以舊 suites 認證新 candidate。

### R3：驗證工具未先通過最小 preflight，反覆製造新阻塞

**runner 事實：**舊工具以自身相對目錄推算 root：

```python
HERE = Path(__file__).resolve().parent.parent
REPO_ROOT = HERE.parents[3]
EVIDENCE = HERE / 'evidence'
```

把預期在 `CON/checks/` 的工具複製到 CON 根目錄，讓 cwd 變成 `/Users/hsiaojohnny/Documents/ChatGPT`，而不是 `Line_backup`；收據也落到 sibling `continuations/evidence`。原 Plan 已要求 task-local 固定 cwd／output，因此這是實作與執行前核對問題。[E10–E12]

**基線事實：**舊清單以 Git 路徑為重要來源，沒有覆盖整個 filesystem namespace；現場既有 FIFO 未被記錄。基線腳本第一輪又有 `current_paths` 未定義；其後遇 FIFO 即中斷，仍用空 records 執行歷史比較。`py_compile` 另留下 CON 內 cache 副作用。[E13–E15]

更早的 live03 報告已記錄 14 個範圍外 artifacts：task-root evidence 8 個、src cache 6 個。歸因於測試與一次未帶 `-B` 的 snapshot，是報告中有時間／路徑支持的推論；原件保留，不能補成完整 actor 證明。這顯示輸出位置與 cache 副作用不是第一次出現。[E04]

**責任：**Planner 須定義所有既有物件類型的保全語意及 baseline bootstrap；Implementer 須在小 fixtures 上先驗證路徑、類型、完成旗標、失敗傳播與輸出副作用，再啟動大盤點或產品 suite。工具放錯位置不能用產品錯誤來命名。

**下輪方向：**保留 recovery-02 已得的本地 PASS；補足尚未閉合的保全輸出時序。工具要有固定根、寫入前 path/scope/ID 檢查、獨立 host 收據及完整／partial 明確狀態。未完成掃描須阻塞 delta 判定，不能把「沒有掃到」變成「已不存在」。

### R4：最新保全失敗——觀察工具把自己的尚未完成輸出納入了穩定性比較

**直接事實：**`compare-preservation.json` 的 baseline→preservation delta 子結果是 PASS，但 preservation-01→02 的 consistency 子結果是 FAIL，總結果及 `preservation-recovery-02.json` 都是 FAIL。它列出七筆失敗，集中在三個 RUNROOT 內的 stdout／stderr 路徑：[E20、E21]

- `tmp/inventory-preservation-02.stdout` 與 `.stderr`：兩筆 `ADDED_NOT_ALLOWED`。
- `tmp/inventory-preservation-01.stdout`：由 0 bytes 變成 725 bytes，bytes／size／hash／mtime／ctime 共五筆 `FIELD_MISMATCH`。

**程式事實：**comparison 的 `SELF_OUTPUTS` 只列四份 inventory JSON；consistency comparison 只允許這組新增。它沒有把上述 stream 檔案的建立與完成時序一併處理。[E22]

**根因推論：**掃描時看到了尚未寫完的自身輸出，後一次看到了完成輸出與新 stream 檔，因此觀察行為改變被比較集合。這是由差異內容及 comparison 程式支持的首要假設；仍應由 Implementer 完整命令／redirect 順序確認，不能只憑 receipt 推定所有執行細節。

還有一個獨立的證據政策問題：`make_planned_additions.py --final` 從第二次 preservation inventory 與 baseline 的實際差集生成 `post_baseline_additions`；現場該清單 `finalized_at_utc=03:17:09Z`，在比較前生成。**事後實際變更清單可以描述發生了什麼，不能單獨證明那些變更事前已核准。** 是否另有不可變、事前凍結的相同允許清單，須等完整交付核對。本報告不據此宣告未授權，也不把 delta 子結果 PASS 擴張成全部變更已授權。[E22、E24、E25]

**下輪方向：**在掃描前凍結精確的輸出路徑與發布順序；明確處理 stream、inventory、比較收據及報告的完成邊界。例如在掃描期間先由 host 持有 stream，完成後按已核准的精確尾段清單 exclusive 發布與 readback，再檢查尾段差異；具體方案由新版 Plan 定義。不能整個豁免 `tmp/` 或 `evidence/`，不能修改舊 FAIL，也不能事後把所有實際變更都自動列成允許。

這次目前列出的差異不構成「備份照片被破壞」的證據；也還不足以宣稱完整 preservation 已通過。應保持局部 PASS、總保全 FAIL 與產品 E2E 未執行三者分開。

### R5：局部復原輪缺少明確返回產品目標的出口

**事實：**recovery-02 Plan 明確只修本地工具並離線驗證 unchanged adapter；production analyzer、native 配對、LINE UI 與真實下載不在該輪範圍。截點仍未看到 Plan04 所列的新 `live_analyzer.mjs`、該輪 `live_runner.mjs` 與 `PassiveContextObservation.swift` 檔案。[E16、E17]

**界線：**特定檔案不存在是現場事實，不等於全 repo 沒有可重用能力；新版 Replanner 須核對其他並行任務與實際來源，避免重做已有元件。

**因果推論：**本地保全修復可以是必要前置；若交付後沒有明確返回真實連接的工作與驗收，就會再增加一輪工具／文件工作，而沒有縮小核心產品未知。

**責任：**跨輪 Replanner 要維持整體目標與依賴圖。我的先前說明過度集中近期 FIFO／runner，應更正：它們是目前與近期直接阻塞，不能充分解釋整條歷史，也不能承諾修好就可立即下載。

**下輪方向：**收到 Implementer 結果後，一次整理剩餘工具阻塞與 production 缺口，提出能直接實測的最小整合計畫；不要求 Implementer 擅自跨越現有範圍，也不再以文件完整作產品完成條件。

## 8. 下一輪建議規劃方向：用最小真實測試找答案

這一節是給正式新版 replan 的設計要求。應在 Implementer 完整結果到齊後，根據新事實收斂；現在不提前凍結命令、產品 patch 或授權擴張。

### A. 先收斂本次結果，保留可用成果

閱讀原始 command／stdout／stderr／receipt，核對 PASS 的 source/hash 與 FAIL 的根因；區分 runner 自測、fake adapter 回歸、完整盤點與真實 LINE。將剩餘保全問題限定成一個可重現的問題，明列輸出時序與驗收，不把整套工具重寫當預設答案。

依 reviewed contract 判斷機械修補可否沿用已有授權；若需變更證據政策、gate、資料邊界或架構，形成新計畫。新 Plan 要把必要工具復原與首個產品真實測試的依賴／出口一起寫清楚。

### B. 首個產品里程碑：一條可供現有流程使用的真實唯讀鏈

**本次要回答：**今天的程式，能否從實際 LINE 畫面，自行產生正確且下游可接受的列表 observation？

**最小實作：**選定一個正式、可呼叫的入口，串接現有 capture、retain、analyzer、native support、classifier／validator。入口只修缺的接點，不建立第二套 state writer／下載 authority。計畫必須說明實際 CUA host／持續 kernel 與本地 runner 如何交換原始資料；不能只留 `analyzeCapture` callback 名稱。

**實測順序：**完成必要授權與工具前置後，取得新鮮真實 LINE capture；留存 screenshot／AX 並驗 hash／readback；取得必要同窗口原生旁證；正式 analyzer 產生候選；下游 validator／catalog 讀取相同 evidence 並回傳接受或拒絕原因。

**成功證據至少包括：**

- 真實原始 screenshot／AX refs、bytes/hash、capture 起迄時間與 session/PID/window/layout 身份。
- 原生窗口／幾何與 frame support 原件及配對關係，不套固定 Retina scale 或猜 crop origin。
- 程式產生的群組、相簿日期／張數、bounds、boundary／focus／eligibility 與依據。
- 正式下游消費者實際接受的輸出；人眼核對另記 OBSERVED，不能替代工具 PASS。
- 同次留存的失敗樣本與具體錯誤，供直接回歸重播；舊 frame 不可拿去派送新 GUI 動作。

**失敗時：**指出第一個不成立的接點，保留最小重現，據此做下一個有界修補；不在沒有新資訊時反覆跑全套。這一步通過代表最小真實觀察鏈可用，仍不是完整備份 E2E。

### C. 接著完成一本真實交易，將觀察鏈延伸到實際檔案與狀態

**本次要回答：**正式觀察與 transaction 能否在同一本真實 eligible 相簿上閉合？

將「確認目標 → detail／menu 校準 → duplicate／目的地／owner／持久 intent → 唯一 Save All 派送 → chooser 確認 → 實際下載 → 完整內容驗收 → canonical state commit／readback → release」接成可追溯流程。UI 校準、交易完成與內容驗收各由自身證據判定。

需要 LINE 前景的精確動作先公告並等待明確交接；中途被取回即停，重新交接後重擷取。Save All 前所有必要條件都要 PASS；結果不確定不能再按一次。遇 writer guard、未知下載、異常目的地或 state drift，依既有安全 recovery 處理，不換 writer、不刪資料、不遷移狀態來迎合測試。[E01、E03]

若 B 已成功而 C 尚未成功，保留已證成的真實觀察鏈，集中分析失敗階段；不能將整體進度歸零，也不能以單本未完成冒稱 E2E 完成。

### D. 再以實際 scroll 與第二本驗證自動延續

第一本 VERIFIED、readback 與 release 後，回到同群組相簿列表，實際執行一次 bounded **0.25-view-height** scroll，保留操作前／動作／操作後證據。確認同 surface/session/PID/window/layout、完整唯一相鄰卡片的有序 overlap，以及至少一張新完整候選的日期與張數；再選另一個 eligible 相簿，重跑完整交易與內容／state 驗收。[E01]

第二本原本可見也不能省略實際 scroll；不能重開剛驗證的第一本湊案例。沒有下一本記 `NO_ELIGIBLE_TARGET`；沒有執行 scroll 記 `SCROLL_TEST_NOT_RUN`／PARTIAL。若版面不足，先依新 Plan 的明確授權處理版面，再 fresh capture，不能猜點或連續盲滾。

### E. 每輪測試都必須真的餵回規劃

| 每輪需要回答 | 報告中的必要內容 |
|---|---|
| 原本相信什麼？ | 一個可被反證的具體假設與預期輸出。 |
| 實際怎麼測？ | 真正入口、命令／工具、source/hash、環境、資料來源與動作順序。 |
| 看到了什麼？ | 原始檔／截圖／stdout／stderr／收據，以及相對／絕對路徑和 hash。 |
| 與預期差在哪？ | 第一個失敗接點、前後狀態、副作用與未執行項目。 |
| 是否更接近目標？ | 這次新增的真實能力、排除的假設及仍然未知的內容。 |
| 下一個動作是什麼？ | 依據新證據的有界修補或決策；同一問題額度與再次失敗時路由。 |

下一版 Plan 不能只列「實作並跑 E2E」，也不能只交付更完整的文件。應指定首個真實實測何時發生、採用哪個 production 入口、以哪些原件判定、在哪個錯誤立即停止，以及成功後如何接到下一段交易。

## 9. 等 Implementer 回來後，Replanner 的工作順序

1. **先更新事實：**以新報告與原件核對第 7 節；本報告的截點狀態若已過時，標記被哪份新證據取代，保留原歷史。
2. **再核對根因：**確認 R4 的輸出時序假設，檢查事前允許清單與事後觀察清單，判斷還有哪些真正阻塞；不要把七筆比較錯誤當七個不同 root issues。
3. **盤點真實入口：**查實際程式與並行成果，逐段列 producer／retain／analyzer／native support／consumer 的現況，確認哪些已存在、哪些缺少、哪些只有 mocks。
4. **提出新版有界 replan：**保留使用者的完整自動備份目標；以 B 的最小真實連接為首個產品 milestone，指定必要修補與檢查，接上 C／D 的交易和實際 scroll 驗收。若不能同輪完成，寫出精確分輪出口。
5. **凍結可執行契約並交 implement：**明列路徑、執行入口、資料與 owner 邊界、gates 的 criticality／evidence role／closure gate、額度／停止條件與報告責任；按適用風險規則處理必要 review，不能擅自取消父任務 Acceptance。
6. **持續循環直到完整驗收：**E2E 產生新證據 → 判斷假設與進度 → replan。只有所有適用必要 gates／reviews 真正滿足，才可關閉整體目標。

新版 replan 的關鍵品質檢查只有一個直接問題：**照這份計畫執行，最早哪一步能用真實 LINE 資料回答產品是否真的接通？** 若回答仍然只有離線 suites、文件或未接線的接口，該計畫尚未解決本次主要根因。
