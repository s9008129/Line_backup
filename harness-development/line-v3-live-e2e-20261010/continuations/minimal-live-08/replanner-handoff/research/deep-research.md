# ML08 深度研究：長期阻塞根因、技術可行性與有界修復路徑

研究日期：2026-10-12。範圍是既有證據和 source 的唯讀分析，以及 Apple、LINE 官方文件查證；未呼叫 CUA、未操作 LINE、未截取新畫面、未執行 build/test，也未改產品或 controller。這份報告是 Planner 的研究輸入，不是新 Plan、前景交接、授權或 gate PASS。

## 結論先行

目前「長期卡住」的直接原因首先是**Harness 流程／授權准入不匹配**，不是已證明 LINE 不可自動化，也不是一次真實 CUA/AX/SCK 操作失敗。已消耗的 C6 單次窄 issue continuation 沒有支援的方式同時完成其修正並返回原任務完整 IMPLEMENT gate 流程；task 現為 `BLOCKED`、`active_run_id=null`、`accepted_gates={}`。所以現在的實機測試前置條件是由 Replanner 先決定一個保留原始身份、歷史、budget、全部 gates 的合法 controller route；本研究不能代替該 route。

產品層也存在具體的靜態缺口：目前 analyzer 只產生 `ALBUMS` 成功結果；runner 需要但尚未提供八個 live action；chooser branch 尚未實作，Native traversal index 到 CUA `setValue` 的 index resolver 契約未證明；沒有觀察到任何實際 `setValue` dispatch 或錯誤輸入。Scrollbar `minimum/maximum` 被硬編碼成 0/1。這些是程式尚未實作或契約缺證據，不能寫成已做過但失敗的 LINE 實驗。

**技術可行性結論為「有合理可行路徑，但尚未證實」。** Apple 提供讀取 AX tree、讀取 SCWindow/window ID、指定單一視窗擷取的正式 API；LINE 官方文件列出 Mac 相簿的 Save all 到資料夾流程。這些只證明平台與產品有相關能力，不證明 LINE 當前各畫面會暴露所需 AX 屬性，不證明 CUA 可用的元素索引等於 Native AX 順序，更不證明兩者能在同一時間、同一實際 window/frame 上可靠配對。下一步應在合法 admission 和使用者明確前景交接後，先做一個只讀、限一次的 live feasibility slice：以一組 paired observation（CUA 一次 `getAXStateAndScreenshot`，同一 capture 含 screenshot 與 AX；Native AX before/after；針對選定 window 的 SCK 單窗擷取一次）檢查同一 LINE surface、window identity binding、唯一完整候選卡片及該配對鏈的 timing。這一步只證明 ALBUMS identity/full-card/timing 基礎，不證明 menu 或 chooser；那些只能在後續另行核准的 stage 驗證。失配即保存原始輸出並停止，不派送 Save All。不要先完成整套 28 項 gate 才允許這個有界診斷，但原 task 中的前置 admission / baseline / auth / preservation 條件仍按核准計畫執行，所有交易及兩相簿 gate 保持為各自的完成結果。

## 從目標倒推必要不變條件與介面

完整目標至少包含一條可重複交易鏈：辨識正確群組與相簿 → 排除已驗證相簿 → 建立唯一 owner 和持久 intent → 在新鮮且可配對的視窗上定位原生 Save All → 用一次性權限派送 → 確認真正的 LINE folder chooser、目的地與下載開始 → 驗證所有檔案內容 → 原子提交 VERIFIED 與狀態 readback → 釋放 owner → 重新取得列表畫面、實際 bounded scroll 並驗證有序 overlap/new candidate → 第二筆獨立交易 → 批次狀態及獨立 Acceptance。

不變條件是：使用者前景交接是即時前置，不可由歷史截圖代替；所有 action 點要由該次 fresh capture 地面化；未證實／逾時的 Save All 或 chooser confirmation 結果不得重送；destination 和 file validation 必須來自真實下載；owner 完成交易後先釋放，再進入列表/scroll 流程；第二筆要是新 eligible album；每個 gate 僅由自己的當前證據判定。LINE 官方說明確有 Windows/Mac Save all 和選資料夾步驟，但沒有聲稱有可供本專案使用的公開 album-download API；本研究未找到可支持這種 API 主張的官方材料。[LINE Help Center：相簿建立、編輯與儲存](https://help.line.me/line?contentId=20000248)

觀測／輸入介面必須是可驗證的閉環，而非把不同工具的序號直接互用：保存同次 capture 的原始圖像與 CUA AX tree；確認 app bundle、PID/process instance、CUA window inventory id/title、AX window number 與 CG/SCK `windowID` / owner PID / frame；從已辨識的 SCWindow 擷取對應畫面；把 OCR 的日期、張數與邊界綁到同一完整 card；輸入端只收該 fresh CUA tree 真正提供、同 frame 有效的 CUA element index，或使用同次 fresh screenshot 地面化的坐標。**已查到本 session 提供的實際 CUA runtime docs**：`getAXState({emit?,disableDiffing?})` 回傳 tree；`getScreenshot()` 回傳 image bytes；`getAXStateAndScreenshot(...)` 同時回傳 `{state,screenshot?}`；`click(number|[x,y])`、`setValue(elementIndex,value)`、`pressKey(key)`、`scroll(target,direction,pages?)`，App 還提供 `scroll(target,direction,distance?:number|{pixels})`；`cua.listApps()` 對各 AppInfo 可帶 `windows:[{id,app,title?}]`。Screenshots-only 後要取 fresh tree 且 disableDiffing，之後才可用 fresh CUA index action；每次 UI action 後要重新取 fresh AX state。這些是工具文件能力，不是本機即時執行證據；CUA 和 Native AX indices 是兩種 index namespace。docs 沒證明 macOS `WindowInfo.id` 等於 CGWindowID，也沒證明 `getApp({windowId})` 在 macOS 可用；文件只指出 native 多窗口需依 title 明選，不能取第一個未知窗口。Apple 定義 `SCWindow.windowID` 是 Core Graphics window ID，並提供 owning application、frame、layer 與 on-screen 狀態；`SCContentFilter(desktopIndependentWindow:)` 可限定只擷取指定 SCWindow。這建立了可設計一致性檢查的官方材料，但**沒有**建立 CUA frame 和原生 window 的現場對應證據。[Apple SCWindow](https://developer.apple.com/documentation/screencapturekit/scwindow)；[Apple 指定視窗的 SCContentFilter](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init%28desktopindependentwindow%3A%29)；[Apple ScreenCaptureKit 擷取說明](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos?language=objc)

### Timing 與 full-catalog feasibility

Static source shows bounded age constraints, not known failures. Adapter `fresh(frameId)` compares monotonic now against CUA `getAXStateAndScreenshot` request **start**, with a 5,000 ms maximum; `observe()` anchors that start before CUA capture, then performs evidence retention, another Native context capture, analysis/classification, and classifier SCK frame support before `latest` is available for actions (`scripts/line_backup_cua_adapter.mjs:93-145`; Q `live_classifier.mjs:155-177`). `originalIntent` and dispatch also require a fresh frame; dispatch permission is consumed before the first UI call (`scripts/line_backup_cua_adapter.mjs:226-280`). The source cannot establish whether a real run completes within this window. A bounded read-only probe should record every phase's start/end and capture-start age at completion; if the chain exceeds deadline, stop before input and preserve the timing breakdown. Never retimestamp captures or weaken expiry.

Catalog has a separate bound. `catalog()` validates each full-list record through `frame(...max_age=600)` and requires the first record to prove top, last to prove bottom, and adjacent views to overlap (`src/line_backup_batch/observations.py:609-635`). `service.admit()` performs this complete validation before writing admitted identities (`src/line_backup_batch/service.py:87-101`); `service.finish()` requires a final catalog and exact identity match with the admitted manifest (`service.py:563-586`). We don't know the number of cards/pages or scan latency for this LINE group, so don't assume a full scan remains under 600 seconds. The current `config/line_backup_config.json` separately uses `max_wait_seconds=600` for download wait; this does not establish catalog acquisition duration. The first capability experiment can stay one read-only frame and avoid formal `admit`; it must not be presented as catalog admission. If catalog freshness conflicts with a minimally bounded diagnostic under the frozen gates, Planner must explicitly define a separate feasibility gate while preserving formal full-catalog admission unchanged.

There is a second semantic conflict within the lifecycle. `finalize()` verifies content and clears album-level writer/context/current-run ownership (`src/line_backup_batch/service.py:475-531`), but leaves the enclosing batch owned. `finish()` transitions that batch to terminal only after catalog validation; then `release()` clears the batch owner (`service.py:563-603`). Thus current flow requests `final_records` before release, while project constitution requires release before returning to the list for fresh observation/scroll. The c6 erratum proposes using admitted catalog within 600 seconds; source validation could accept it if still fresh enough, but those records predate the download and do not prove post-transaction collection stability. This does not automatically prove that service must change: Planner must freeze what `final_records` means and which drift condition the acceptance gate requires. If replaying admitted records is acceptable, a bounded runner/adapter ordering change might suffice, subject to age and gate review. If drift evidence must represent a genuinely post-transaction album list before release, current service order cannot satisfy both requirements; a new service/API semantic plan or separate evidence contract is needed. This changes protected behavior/path scope and is outside C6. `stop()` has conditional semantics: with a current album it records the album stop/abort path; after `finalize()` has cleared the current album, it can terminalize the batch without validating the final catalog. Neither path proves the frozen normal `finish()` catalog/drift condition. It must not replace `finish()`, and this report does not claim that every `stop()` rewrites a VERIFIED album as SAFE_ABORT.

## 平台／產品官方資料與可證明範圍

Apple AX API 可列舉 AX element 支援的 attribute 和 action，也可以查詢屬性值；Apple 亦明確列出 `attributeUnsupported`、`noValue`、`invalidUIElement`、`cannotComplete` 等失敗情況。這代表 AX 必須以現場讀取結果做能力探測，不能因標準化名詞存在就假設 LINE 對每個 element 都暴露它。具體而言，Native observer 的 window identity path 硬性要求 `AXFocusedWindow`、`AXWindows` 中 window element 的 `AXWindowNumber` 能讀取且相符；首個 live probe 須記 supported attribute names、讀值結果與實際 number，沒有就記明確 absent/error 並停止該配對分支。Apple `SCWindow.windowID` 是 CG identifier，但這不保證 AX 對 LINE 暴露 `AXWindowNumber`；Apple `NSWindow.windowNumber` 文件也特別區分 app window-device number 與 window server global number，因此不能跨 namespace 直接類比。[AXUIElementCopyAttributeNames](https://developer.apple.com/documentation/applicationservices/1459475-axuielementcopyattributenames)；[AXUIElementCopyAttributeValue](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue)；[SCWindow.windowID](https://developer.apple.com/documentation/screencapturekit/scwindow/windowid)；[NSWindow.windowNumber](https://developer.apple.com/documentation/appkit/nswindow/windownumber)

Apple ScreenCaptureKit 提供可列舉 SCWindow 和只擷取指定 SCWindow 的 content filter。因 SCWindow 提供 CG window ID、app、frame、on-screen 等值，合理的最佳實務是把同一即時 PID/window/frame/時間關係當成明確前置約束，不用「同尺寸視窗」或舊窗口 ID 猜測。這仍只證明實作可以嘗試建立配對；必須由下一個真實輸出證明 LINE 的 AX/CG/SCK/CUA 確實指向同一窗口。[SCShareableContent](https://developer.apple.com/documentation/screencapturekit/scshareablecontent)；[SCWindow](https://developer.apple.com/documentation/screencapturekit/scwindow)；[specified-window SCContentFilter](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init%28desktopindependentwindow%3A%29)

LINE 官方說明明確包括 macOS/Windows 相簿 `Save all`、選資料夾及確認的操作順序。它支持選 UI 自動化而非虛構網路 API 的方向；不表示它保證相同按鈕文字、menu window AX、固定 geometry 或當前 CUA app 能執行相同操作。[LINE Help Center](https://help.line.me/line?contentId=20000248)
